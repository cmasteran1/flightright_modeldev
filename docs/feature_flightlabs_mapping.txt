================================================================================
FEATURE → FLIGHTLABS API MAPPING REFERENCE
Flight Delay Prediction Models (Departure & Arrival)
Last updated: 2026-03-13  (rev 3 — positional hub feature naming (hub_0_/hub_1_/...),
             updated to v7g feature set, all-carrier history pool now enforced in code)
================================================================================

This document describes every feature used by the departure delay model (v7g)
and the arrival delay model (v7g arr) in plain English, and maps each one to a
strategy for computing it using the FlightLabs API instead of BTS data.

Where used:
  [DEP] = Departure delay model only
  [ARR] = Arrival delay model only
  [BOTH] = Used in both models

IMPORTANT SCOPE NOTE
--------------------
Two categories of BTS features are NOT reproducible from FlightLabs and are
therefore DROPPED from any live inference pipeline:

  (1) Delay cause-code features — BTS classifies delay by cause (carrier,
      NAS, weather, late-aircraft, security). FlightLabs returns only total
      delay minutes. Figuring out the cause reliably requires data that
      arrives days to weeks after the flight (ASPM/OOOI records, airline
      operations logs). These features are dropped:
        carrier_lateaircraft_rate_last1/7/14
        origin_lateaircraft_rate_last1/7/14
        origin_nas_rate_last1/7/14
        origin_weather_rate_last1/7/14
        tail_lateaircraft_rate_last1/7/14
        dest_lateaircraft_rate_last1/7/14
        hub_{I}_lateaircraft_rate_last{W}  (I=0..4 for WN v7g; all windows)

  (2) Tail-specific delay history — tail_depdelay_mean_last1/7/14. Even
      though past tail data could be obtained from Flight Data by Date
      (search_by=reg), the current flight's tail assignment is not
      deterministically knowable before departure without internal airline
      records. These features are dropped. Turn/rotation features ARE kept
      using the inbound-chain inference described in Section 3C.


================================================================================
SECTION 1 — FLIGHTLABS ENDPOINT REFERENCE
================================================================================

All calls are HTTP GET. Substitute YOUR_KEY for your access_key.

  A. FLIGHT DATA BY DATE  (primary per-flight historical source)
     URL:  https://app.goflightlabs.com/v2/flight
     Required params:
       access_key={KEY}
       search_by=number   (also accepts: reg, callsign, icao24)
       flight_number={IATA flight code, e.g. WN1234}
       date_from={YYYY-MM-DD}
       date_to={YYYY-MM-DD}   ← must be ≤ 14 days after date_from
     Key response fields (per flight record):
       departure.iataCode         – origin airport IATA
       departure.scheduledTime    – scheduled departure, ISO local timestamp
       departure.runwayTime       – actual departure (off-block), ISO local
       departure.revisedTime      – estimated/revised departure (if different)
       arrival.iataCode           – destination airport IATA
       arrival.scheduledTime      – scheduled arrival, ISO local
       arrival.revisedTime        – actual/estimated arrival, ISO local
       aircraft.reg               – tail / registration number (e.g. "N8710Q")
       aircraft.model             – aircraft model string (e.g. "Boeing 737-800")
       greatCircleDistance        – object with .miles, .km, .nm (route distance)
     Derived fields:
       dep_delay_min = runwayTime − scheduledTime (departure)
       arr_delay_min = revisedTime − scheduledTime (arrival)
     Cost note: One call returns all instances of ONE flight number over
                the specified date range (up to 14 days). Ideal for computing
                per-flight rolling statistics. To build a 14-day window, one
                call per flight number suffices.

  B. FLIGHT SCHEDULES  (primary airport-level historical source)
     URL:  https://app.goflightlabs.com/advanced-flights-schedules
     Params: iataCode={AIRPORT}, type={departure|arrival},
             airline_iata={IATA}  (optional filter)
     Key response fields:
       flight_iata, flight_number, airline_iata
       dep_iata, arr_iata
       dep_time           – scheduled departure, "YYYY-MM-DD HH:MM" local
       dep_actual         – actual departure, local
       dep_delayed        – departure delay in minutes
       arr_time           – scheduled arrival, local
       arr_actual         – actual arrival, local
       arr_delayed        – arrival delay in minutes
       duration           – scheduled flight duration, minutes
       aircraft_icao      – aircraft type ICAO code (e.g. "B738")
       status             – landed / cancelled / active / etc.
     Cost note: One call returns ALL flights for ONE airport for roughly
                the current day. Used for bulk airport-level statistics and
                for the inbound-chain rotation inference. Pull nightly per
                airport per airline.

  C. FUTURE FLIGHTS PREDICTION  (prediction-time only)
     URL:  https://app.goflightlabs.com/advanced-future-flights
     Params: iataCode={AIRPORT}, type={departure|arrival},
             date={YYYY-MM-DD}
     Key response fields:
       carrier.fs              – airline IATA code
       carrier.flightNumber    – numeric flight number
       airport.fs              – counterpart airport IATA
       departureTime.time24    – scheduled departure HH:MM
       arrivalTime.time24      – scheduled arrival HH:MM
       sortTime                – ISO timestamp for ordering
     Cost note: One call returns all scheduled flights for ONE airport on
                ONE date. Used at prediction time for congestion counting.

  D. AIRPORTS  (one-time metadata cache)
     URL:  https://www.goflightlabs.com/airports
     Params: iataCode={AIRPORT}
     Key response fields: iata_code, lat, lng, timezone, name, city
     Cost note: Pull once per airport, cache permanently. ~100 US airports
                covers any domestic carrier.

  E. OPEN-METEO  (not FlightLabs — free, no key required)
     Historical: https://archive-api.open-meteo.com/v1/archive
     Forecast:   https://api.open-meteo.com/v1/forecast  (≤ 7 days ahead)
     Used for ALL weather features. Already implemented in prepare_dataset.py.


================================================================================
SECTION 2 — DATA COLLECTION STRATEGY (MINIMIZING API COST)
================================================================================

DATA FLOWS ARE SEPARATED INTO THREE TIERS:

TIER 1 — One-time setup (run once, refresh rarely)
  - Airport metadata: ~100 calls to Endpoint D. Cache lat/lng/timezone.
  - ICAO→IATA aircraft type mapping: static file from OpenFlights/OurAirports,
    no API calls. Refresh annually.
  - FAA aircraft registry: free CSV download from faa.gov, needed only if
    Aircraft_Age_Bucket is retained. Refresh annually.

TIER 2 — Nightly offline batch (builds the rolling-stats database)
  For each airline served (e.g. WN):
    For each airport the airline serves (~50 for WN):
      GET /advanced-flights-schedules?iataCode={AP}&type=departure&airline_iata={WN}
      GET /advanced-flights-schedules?iataCode={AP}&type=arrival&airline_iata={WN}
      → Store in local database. Use to compute all airport-level and
        carrier-level rolling stats (1/7/14-day windows) locally.

  For hub spillover (all carriers at hub airports):
    For each hub in {DEN, PHX, BWI, MDW, BNA}  (WN v7g; hub_0..hub_4):
      GET /advanced-flights-schedules?iataCode={HUB}&type=departure
      → All-carrier data for hub delay stats. Do NOT filter by airline_iata —
        hub congestion is a network-wide signal; filtering to one carrier would
        produce sparsely-populated or all-NaN hub features for any non-dominant
        carrier at that airport.

  TOTAL: ~50×2 + 5 = 105 calls per airline per night.

  Per-flight-number rolling stats (flight number + OD pair):
    These are pulled ON-DEMAND at prediction time using Endpoint A rather
    than nightly, because the number of distinct flight numbers is large and
    most are never predicted. One call per unique flight number retrieves
    up to 14 days of history. Cache results by (flight_number, last_refresh)
    with a TTL of ~12 hours to avoid redundant calls for the same flight
    within a day.

TIER 3 — Prediction-time queries (per prediction, 2 calls minimum)
  Call 1: Future Flights at Origin
    GET /advanced-future-flights?iataCode={Origin}&date={FlightDate}&type=departure
    → All departures at origin that day. Used for: congestion counting,
      flight schedule confirmation, first-leg-of-day check.

  Call 2: Future Flights at Destination
    GET /advanced-future-flights?iataCode={Dest}&date={FlightDate}&type=arrival
    → Used for: destination arrival congestion features.

  Call 3 (conditional): Flight Data by Date for rolling stats
    GET /v2/flight?search_by=number&flight_number={WN1234}&date_from={D-14}&date_to={D-1}
    → Only called if this flight number is not already in the local cache
      from a recent prediction. Cached with ~12-hour TTL.

  Weather (Open-Meteo, free):
    2 calls: one for origin (daily + hourly), one for destination (hourly).

  TOTAL FlightLabs calls at prediction time: 2–3.

SECTION 3 — FEATURE-BY-FEATURE MAPPING
================================================================================

────────────────────────────────────────────────────────────────────────────────
3A. CATEGORICAL / IDENTITY FEATURES
────────────────────────────────────────────────────────────────────────────────

FEATURE: Reporting_Airline [BOTH]
  What it is: The IATA two-letter code for the operating airline (e.g. "WN"
              for Southwest). Used as a categorical feature to capture
              airline-specific operational tendencies.
  BTS source: Reporting_Airline column.
  FlightLabs: airline_iata from any endpoint. Known as an input to the
              prediction request. No API call needed.

FEATURE: Origin [BOTH]
  What it is: IATA three-letter code for the departure airport (e.g. "DAL").
  BTS source: Origin column.
  FlightLabs: departure.iataCode from Endpoint A, or dep_iata from B/C.
              Known at query time. No extra API call needed.

FEATURE: Dest [BOTH]
  What it is: IATA three-letter code for the arrival airport (e.g. "MDW").
  BTS source: Dest column.
  FlightLabs: arrival.iataCode from Endpoint A, or arr_iata from B/C.
              Known at query time.

FEATURE: od_pair [DEP]
  What it is: Combined "Origin_Dest" string (e.g. "DAL_MDW"). A single
              categorical capturing route-level effects. Routes with
              historically tight schedules or difficult airspace show up here.
  FlightLabs: Derived from Origin + "_" + Dest. No API call needed.

FEATURE: DepTimeBlk [BOTH]
  What it is: Scheduled departure time block in HHMM-HHMM format grouping
              by hour (e.g. "1400-1459"). Captures airport congestion
              rhythms that repeat at the same time each day.
  BTS source: Pre-computed DepTimeBlk column.
  FlightLabs: Derived from departure.scheduledTime — parse HH, format as
              "HH00-HH59". No extra API call needed.

FEATURE: aircraft_type [BOTH]
  What it is: IATA aircraft type code (e.g. "73H" for Boeing 737-800).
              Different aircraft have different performance profiles,
              maintenance schedules, and delay tendencies.
  BTS source: BTS aircraft type from tail lookup.
  FlightLabs: aircraft.model from Endpoint A (Flight Data by Date) gives a
              string like "Boeing 737-800". Map this to the IATA code via a
              static conversion table (freely available from OpenFlights).
              Alternatively, Endpoint B returns aircraft_icao (e.g. "B738"),
              which maps to IATA via the same table.

FEATURE: Aircraft_Age_Bucket [BOTH]
  What it is: Bucketed aircraft age in years (e.g. "0-5yr", "6-10yr",
              "11-15yr", "16+yr"). Older aircraft have more maintenance events.
  BTS source: Join on tail number to FAA aircraft registry for year built.
  FlightLabs: aircraft.reg from Endpoint A gives the tail/N-number. Look up
              year of manufacture in the FAA Aircraft Registry CSV (free
              download from faa.gov). Compute age = current_year - mfr_year,
              then bucket. Cache tail→age permanently (refresh annually).
              Note: this requires knowing the tail of the current flight —
              see Section 3C for the rotation inference strategy. If tail
              assignment is unavailable at prediction time, default to the
              fleet average for this aircraft type.

FEATURE: is_holiday [BOTH]
  What it is: Binary (0/1). Is the departure date a US federal holiday?
              Holidays drive surge demand and higher delay rates systemwide.
  FlightLabs: No API call needed. Use the Python 'holidays' package or a
              static calendar. Apply to the flight date.

FEATURE: is_spring_break [BOTH]
  What it is: Binary (0/1). Does the departure date fall in typical spring
              break travel windows (mid-March through early April)?
  FlightLabs: No API call needed. Static date-range lookup per year.

FEATURE: dep_dow [BOTH]
  What it is: Day of week for scheduled departure (0=Monday, 6=Sunday).
              Fridays and Sundays carry the highest systemic delay risk.
  FlightLabs: Derived from departure.scheduledTime date. No API call needed.

FEATURE: flight_month [BOTH]
  What it is: Month of scheduled departure (1–12). Captures seasonal delay
              patterns: summer thunderstorm season, winter ice/snow.
  FlightLabs: Derived from departure.scheduledTime date. No API call needed.

FEATURE: has_recent_arrival_turn_5h [BOTH]
  What it is: Binary (0/1). Did this aircraft arrive at the origin airport
              from a prior leg within the 5 hours before this departure?
              Mid-rotation aircraft carry delay risk from prior legs.
  FlightLabs: See Section 3C (rotation inference).

FEATURE: is_first_leg_of_day [DEP]
  What it is: Binary (0/1). Is this the first scheduled departure of this
              flight number today? First-of-day departures are not exposed
              to propagated delay from earlier legs.
  FlightLabs: From Tier-3 Call 1 (Future Flights at Origin): find the
              earliest occurrence of this carrier.flightNumber for today.
              If this flight is at or before that time, set to 1.
              Also cross-check against the offline cache for whether an
              earlier departure city exists for this flight number.


────────────────────────────────────────────────────────────────────────────────
3B. SCHEDULE & ROUTE FEATURES
────────────────────────────────────────────────────────────────────────────────

FEATURE: CRSDepTime [BOTH]
  What it is: Scheduled departure time as an integer in HHMM format
              (e.g. 1435 for 2:35 PM local time). Used as a numeric feature
              to capture fine-grained time-of-day delay patterns.
  FlightLabs: Parse departure.scheduledTime from Endpoint A (or dep_time
              from B/C), extract HH:MM, convert to HHMM integer.

FEATURE: CRSElapsedTime [BOTH]
  What it is: Scheduled flight duration in minutes. Longer flights have
              more en-route weather exposure and a tighter schedule buffer.
  FlightLabs: From Endpoint B: duration field (minutes).
              From Endpoint A: compute minutes between departure.scheduledTime
              and arrival.scheduledTime.
              From Endpoint C: minutes between departureTime and arrivalTime.

FEATURE: Distance [BOTH]
  What it is: Great-circle route distance in statute miles. Correlates with
              elapsed time and captures route difficulty.
  FlightLabs: Endpoint A returns greatCircleDistance.miles directly for the
              specific flight queried. This is the cleanest source.
              Alternatively, derive from airport lat/lng (Endpoint D) using
              the haversine formula and cache per OD pair permanently.

FEATURE: sched_dep_hour [BOTH]
  What it is: Scheduled departure hour as an integer (0–23). More granular
              than DepTimeBlk and used as a categorical in the departure model.
  FlightLabs: Extracted from departure.scheduledTime. No API call needed.

FEATURE: sched_arr_hour [ARR]
  What it is: Scheduled arrival hour (0–23). Captures how congested the
              destination is likely to be at the expected landing time.
  FlightLabs: Extracted from arrival.scheduledTime. No API call needed.


────────────────────────────────────────────────────────────────────────────────
3C. AIRCRAFT ROTATION FEATURES (inbound-chain inference)
────────────────────────────────────────────────────────────────────────────────

Background: These features describe how deep into its daily rotation an
aircraft is before departing on this leg. Each additional leg introduces
the possibility of cascaded delay from the prior one.

KEY CONSTRAINT: The tail number (reg_number) assigned to a future or same-day
flight is not reliably obtainable without internal airline scheduling records.
The real-time endpoint is NOT used (it only reflects the current position of
an aircraft already airborne; it cannot be used pre-departure to determine
which aircraft will operate a future flight).

ROTATION INFERENCE STRATEGY (schedule-only, no tail number required):
-----------------------------------------------------------------------
Southwest (and other point-to-point carriers) typically operate a simple
turn pattern: one aircraft arrives at a station, is cleaned and boarded,
then departs. The inbound flight that "feeds" this departure can be inferred
from the offline arrival cache.

For a target departure (carrier C, origin AP, scheduled dep_time T):

  Step 1 — Find the inbound feeding flight:
    In the offline cache for today (already fetched in the nightly Tier-2
    pull for arrivals at AP for carrier C), find the most recent arrival
    that satisfies:
      arr_time ∈ [T − 4h,  T − 0.5h]
    (At least 30 minutes before departure for a legal turn; within 4 hours
    to be a plausible same-aircraft turn for a short-haul network.)
    If multiple arrivals qualify, take the most recent one. Call this
    the "inbound flight I".

  Step 2 — Compute rotation features from I:
    turn_time_hours           = T − I.arr_time  (in hours, scheduled times)
    has_recent_arrival_turn_5h = 1 if I exists, else 0

  Step 3 — Approximate leg number by tracing the chain:
    Recursively apply Step 1 at I's origin airport (I.dep_iata) using
    I.dep_time as the reference time, to find the flight that fed I.
    Count the hops until no valid inbound is found (beginning of day).
    tail_leg_num_day ≈ number of hops + 1.
    Practical limit: trace at most 4 hops (Southwest aircraft average
    ~6 legs/day; a 4-hop trace is sufficient for meaningful bucketing).
    If no inbound is found in Step 1, tail_leg_num_day = 0 (first leg).

  Limitations:
    - At large hubs with many simultaneous arrivals/departures, the
      "most recent arrival" heuristic may pick the wrong inbound. Accuracy
      is highest at spoke airports with sparse schedules.
    - Aircraft swaps due to maintenance or irregular ops are not captured.
    - Accuracy degrades for hub-to-hub flights where multiple inbounds
      arrive in close succession.

FEATURE: tail_leg_num_day [BOTH]
  What it is: Approximate number of flight segments this aircraft has
              already flown today before this departure (0 = first flight).
              Each additional leg adds cumulative delay exposure.
  FlightLabs: Derived from the inbound-chain trace (Step 3 above).
              Uses only offline Tier-2 cache data; no extra API call needed
              at prediction time.

FEATURE: has_recent_arrival_turn_5h [BOTH]
  What it is: Binary. Was there a plausible inbound arrival for this aircraft
              within the past 5 hours? If yes, it is mid-rotation and any
              prior arrival delay propagates.
  FlightLabs: Derived from Step 1 of inbound-chain inference.
              Uses offline Tier-2 cache. No extra API call.

FEATURE: turn_time_hours [BOTH]
  What it is: Scheduled hours between the inferred inbound arrival and this
              departure (e.g. 1.25 h = 75-minute turn). Shorter turns leave
              less buffer to absorb delay. Computed from scheduled times only,
              so it is knowable before departure.
  FlightLabs: Derived from Step 2 of inbound-chain inference.
              Uses offline Tier-2 cache. No extra API call.

FEATURE: flightnum_hours_since_first_departure_today [BOTH]
  What it is: Hours between this flight's scheduled departure and the
              earliest departure of this flight number anywhere today.
              Captures how late in the day this flight number has been
              operating — later instances have had more time to accumulate
              network delay.
  FlightLabs: From Tier-3 Call 1 (Future Flights at Origin) combined with
              the offline Tier-2 cache: find the minimum departure time for
              this carrier.flightNumber across all airports today. Compute
              (this dep_time − earliest dep_time) in hours.
              Note: the first departure of this flight number may originate
              from a different city than Origin; the offline cache covers
              all airports for this airline, so it can be found there.

FEATURE: tail_depdelay_mean_last1 / last7 / last14  ← DROPPED
  What it is would have been: Average departure delay for this specific
              aircraft over recent days — a chronic-maintenance signal.
  Why dropped: The tail number of the aircraft that will operate the current
              flight is not deterministically knowable before departure
              without internal airline records. Even though historical tail
              data is available via Endpoint A (search_by=reg), the mapping
              of tail→upcoming flight cannot be made reliably in advance.


────────────────────────────────────────────────────────────────────────────────
3D. ORIGIN CONGESTION FEATURES
────────────────────────────────────────────────────────────────────────────────

FEATURE: origin_congestion_3h_total [BOTH]
  What it is: Total departures from origin (all airlines) within ±3 hours
              of this flight's scheduled departure. High congestion increases
              ground delays, taxi times, and EDCT slot restrictions.
  FlightLabs: From Tier-3 Call 1 (Future Flights at Origin), which returns
              ALL departures at Origin for FlightDate. Count records where
              |sortTime − target_dep_time| ≤ 180 minutes.
              No extra API call needed.

FEATURE: origin_airline_congestion_3h_total [BOTH]
  What it is: Same ±3-hour congestion count but only for the same airline.
              Captures how strained the airline's own gates and staff are.
  FlightLabs: Same Future Flights response from Call 1; filter on
              carrier.fs == target_airline_iata before counting.
              No extra API call.


────────────────────────────────────────────────────────────────────────────────
3E. WEATHER FEATURES (Open-Meteo — no FlightLabs cost)
────────────────────────────────────────────────────────────────────────────────

All weather features are sourced from the Open-Meteo API (free, no key).
Already implemented in prepare_dataset.py. No changes to this pipeline.

Coordinates come from the airports cache (Endpoint D, Tier-1 setup).

For HISTORICAL dates: archive-api.open-meteo.com/v1/archive
For FUTURE (≤7 days): api.open-meteo.com/v1/forecast

ORIGIN DAILY WEATHER [BOTH] (full-day summary at departure airport):
  origin_temperature_2m_max / origin_temp_max_K  — Daily high temperature
  origin_temperature_2m_min / origin_temp_min_K  — Daily low temperature
  origin_precipitation_sum / origin_daily_precip_sum_mm — Total daily rain/snow
  origin_windspeed_10m_max / origin_daily_windspeed_max_kmh — Max sustained wind
  origin_windgusts_10m_max / origin_daily_windgusts_max_kmh — Max gusts
  origin_weathercode / origin_daily_weathercode — WMO code (0–99):
    0–2 = clear; 3 = overcast; 45/48 = fog; 51–67 = drizzle/rain;
    71–77 = snow; 80–82 = showers; 95–99 = thunderstorms

ORIGIN HOURLY WEATHER [BOTH] (at the scheduled departure hour):
  origin_dep_temperature_2m / origin_dep_temp_K     — Temperature at dep hour
  origin_dep_precipitation / origin_dep_precip_mm   — Precip at dep hour
  origin_dep_windspeed_10m / origin_dep_windspeed_kmh  — Wind at dep hour
  origin_dep_windgusts_10m / origin_dep_windgusts_kmh  — Gusts at dep hour
  origin_dep_weathercode / origin_dep_hour_weathercode — WMO code at dep hour
  origin_dep_visibility / origin_dep_visibility_m   — Visibility (km / meters)
  origin_dep_cape / origin_dep_cape_jkg / origin_dep_log1p_cape
    — Convective Available Potential Energy (J/kg). Values >1000 indicate
      risk of convective delays. Stored raw and as log1p to compress skew.
  origin_dep_cloudcover / origin_dep_cloudcover_pct — Cloud cover percentage

DESTINATION HOURLY WEATHER [ARR] (at the scheduled arrival hour):
  dest_arr_temperature_2m    — Temperature at destination at arrival hour
  dest_arr_precipitation     — Precipitation at destination at arrival hour
  dest_arr_windspeed_10m     — Wind speed at destination at arrival hour
  dest_arr_windgusts_10m     — Wind gusts at destination at arrival hour
  dest_arr_weathercode       — WMO weather code at destination at arrival hour
  dest_arr_visibility        — Visibility at destination at arrival hour
  dest_arr_cape              — CAPE at destination at arrival hour
  dest_arr_cloudcover        — Cloud cover at destination at arrival hour


────────────────────────────────────────────────────────────────────────────────
3F. ROLLING DEPARTURE DELAY STATISTICS
────────────────────────────────────────────────────────────────────────────────

"Last N" windows are calendar days immediately preceding the prediction date,
not including the prediction date itself.

Delay minutes are computed as:
  From Endpoint A: departure.runwayTime − departure.scheduledTime (in minutes)
  From Endpoint B: dep_delayed field directly

────────── FLIGHT NUMBER + OD PAIR STATISTICS ──────────

Source: Endpoint A (Flight Data by Date), searched by flight number.
Strategy: At prediction time (or from TTL cache), call:
  GET /v2/flight?search_by=number&flight_number={WN1234}
                &date_from={D-14}&date_to={D-1}
The response covers 14 days in one call. Filter records by dep_iata=Origin
and arr_iata=Dest to isolate this OD pair (a flight number can serve
multiple route segments over its history). Compute stats locally.

FEATURE: flightnum_od_depdelay_mean_last1 / last7 / last14 [BOTH]
  What it is: Average departure delay (minutes) for this specific flight
              number on this exact origin→destination route over the past
              1, 7, or 14 days. The most direct recent performance signal
              for this specific scheduled flight.
  FlightLabs: From Endpoint A response: filter by dep_iata + arr_iata +
              date in window. Compute mean of dep_delay_min. One API call
              per flight number covers all three windows.

FEATURE: flightnum_od_depdelay_median_last1 / last7 / last14 [BOTH]
  What it is: Median departure delay for this flight number + OD pair over
              past 1, 7, or 14 days. Median is more robust to single bad
              days (e.g. a weather ground stop).
  FlightLabs: Same Endpoint A records. Compute median of dep_delay_min.

FEATURE: flightnum_od_depdelay_std_last7 / last14 [BOTH]
  What it is: Standard deviation of departure delay for this flight + OD
              over past 7 or 14 days. High variance means the flight is
              hard to predict — some days on-time, others severely late.
  FlightLabs: Same records. Compute std of dep_delay_min.

FEATURE: flightnum_od_support_count_last14d [BOTH]
  What it is: How many times this flight number actually operated this OD
              pair in the past 14 days. Low counts mean the rolling stats
              above are based on too few data points to be reliable.
  FlightLabs: Count of Endpoint A records matching this OD pair over 14 days.

FEATURE: flightnum_od_low_support_last14d [BOTH]
  What it is: Binary (0/1). Set to 1 if support count is below 5, signaling
              that the rolling stats should be treated as unreliable.
  FlightLabs: Derived from support count. No API call needed.

────────── CARRIER-WIDE DEPARTURE DELAY STATISTICS ──────────

Source: Tier-2 offline cache (Endpoint B pulled nightly for all airports
served by this carrier). Aggregated across all airports.

FEATURE: carrier_depdelay_mean_last1 / last7 / last14 [BOTH]
  What it is: Average departure delay across ALL flights system-wide for
              this airline over the past 1, 7, or 14 days. Captures airline
              operational health — a high value signals widespread disruption
              such as a ground stop, IT outage, or labor slowdown.
  FlightLabs: From offline cache: all records where airline_iata = target
              airline, date in window. Compute mean of dep_delayed across
              all airports. Coverage requires the nightly pull to include
              all of the carrier's served airports (as planned in Tier 2).

FEATURE: carrier_depdelay_std_last7 / last14 [DEP]
  What it is: Standard deviation of the carrier's system-wide departure
              delays over the past 7 or 14 days. High std indicates
              inconsistent, volatile operations.
  FlightLabs: Same offline cache data. Compute std of dep_delayed.

────────── CARRIER + ORIGIN DEPARTURE DELAY STATISTICS ──────────

FEATURE: carrier_origin_depdelay_mean_last1 / last7 / last14 [BOTH]
  What it is: Average departure delay for THIS airline at THIS origin airport
              over the past N days. Some airlines perform better at their
              hubs (priority resources) and worse at focus cities.
  FlightLabs: From offline cache: filter airline_iata = WN AND dep_iata =
              Origin. Compute mean of dep_delayed over each window.

FEATURE: carrier_origin_depdelay_std_last1 / last7 / last14 [ARR]
  What it is: Standard deviation of departure delay for this carrier at
              this origin over past N days.
  FlightLabs: Same offline cache filter. Compute std.

────────── ORIGIN AIRPORT DEPARTURE DELAY STATISTICS (ALL CARRIERS) ──────────

Source: Tier-2 offline cache (Endpoint B pulled nightly for all carriers).

FEATURE: origin_depdelay_mean_last1 / last7 / last14 [BOTH]
  What it is: Average departure delay at origin across ALL airlines over
              the past N days. Captures whether the airport itself is running
              behind — ATC congestion, construction, or weather affects
              all carriers equally.
  FlightLabs: From offline cache: all records with dep_iata = Origin,
              any airline_iata. Compute mean of dep_delayed.
              Note: the nightly pull collects all-carrier data at hub airports
              already; extend to origin airports as needed.

FEATURE: origin_depdelay_std_last1 / last7 / last14 [ARR]
  What it is: Standard deviation of departure delays at origin (all carriers)
              over past N days.
  FlightLabs: Same offline cache records. Compute std.

────────── DELAY CAUSE-RATE FEATURES — ALL DROPPED ──────────

The following features from the BTS model are DROPPED because reliable
cause attribution is not available from FlightLabs or any other real-time
API at prediction time. BTS cause codes (LateAircraftDelay, NASDelay,
WeatherDelay, CarrierDelay) are assigned by airlines after the fact and
only published in aggregate monthly releases:

  DROPPED: carrier_lateaircraft_rate_last1/7/14
  DROPPED: origin_lateaircraft_rate_last1/7/14
  DROPPED: origin_nas_rate_last1/7/14
  DROPPED: origin_weather_rate_last1/7/14
  DROPPED: dest_lateaircraft_rate_last1/7/14
  DROPPED: tail_lateaircraft_rate_last1/7/14

These features carry substantial predictive signal in the BTS-trained model.
A retraining pass that excludes them (using Endpoint-sourced data only) is
advisable before deploying to production, so the model learns to use the
remaining features optimally rather than relying on their correlation with
the dropped ones.


────────────────────────────────────────────────────────────────────────────────
3G. HUB SPILLOVER FEATURES
────────────────────────────────────────────────────────────────────────────────

Background: The model tracks delay conditions at the airline's designated hub
airports. When these hubs are stressed, delays cascade across the entire
network. For WN v7g the five hubs are: Denver (DEN), Phoenix (PHX),
Baltimore/Washington (BWI), Chicago Midway (MDW), and Nashville (BNA).

NAMING: Hub features use POSITIONAL names (hub_0_, hub_1_, ...) rather than
airport codes, so the same training config and inference pipeline works for
any airline. The mapping from index to airport is defined by the order of
the hubs list in the feature config (features_dep.hub_spillover.hubs).

For WN v7g:  hub_0=DEN  hub_1=PHX  hub_2=BWI  hub_3=MDW  hub_4=BNA

Source: Tier-2 offline cache for each hub — ALL-CARRIER departures pulled
nightly (the 5 hub calls in Tier 2). History pool is intentionally not
filtered by target airline: hub congestion is a network-wide signal that
affects all carriers operating into/out of those airports.

For each hub index I (0-based) corresponding to the hubs above:

FEATURE: hub_{I}_depdelay_mean_last1 / last7 / last14 [BOTH]
  What it is: Average departure delay at hub[I] (all carriers) over the past
              1, 7, or 14 days. High average at a hub signals network stress
              that propagates downstream to all connecting and downstream
              flights.
  FlightLabs: Offline cache for dep_iata = hub[I] (all airlines). Compute
              mean of dep_delayed. No extra API call at prediction time.

NOTE: hub_{I}_lateaircraft_rate_last{W} is DROPPED (delay cause code
required — see Section 3F).

Departure model: windows {1, 7, 14} → 5 hubs × 3 windows × 1 stat = 15 features.
Arrival model:   windows {1, 7, 14} → 5 hubs × 3 windows × 1 stat = 15 features.


────────────────────────────────────────────────────────────────────────────────
3H. ARRIVAL DELAY HISTORY FEATURES [ARR only]
────────────────────────────────────────────────────────────────────────────────

Source: Endpoint A (Flight Data by Date) — same call used for Section 3F
flight-number stats, which also returns arrival.revisedTime.

arr_delay_min = arrival.revisedTime − arrival.scheduledTime  (minutes)

FEATURE: arrdelay_mean_7d_fn_od / arrdelay_mean_14d_fn_od [ARR]
  What it is: Average arrival delay for this specific flight number on this
              origin→destination route over past 7 or 14 days. More directly
              relevant to the arrival delay target than departure history.
  FlightLabs: From the same Endpoint A response used for 3F: filter by
              dep_iata + arr_iata + date window. Compute mean of arr_delay_min.

FEATURE: arrdelay_count_7d_fn_od / arrdelay_count_14d_fn_od [ARR]
  What it is: Count of flight observations for this fn+OD pair over past
              7 or 14 days. Support count for the mean estimate.
  FlightLabs: Count of matching Endpoint A records with valid arrival times.

FEATURE: arrdelay_median_7d_fn_od [ARR]
  What it is: Median arrival delay for this flight number + OD pair over
              past 7 days. Robust to outlier days.
  FlightLabs: Endpoint A records. Compute median of arr_delay_min.

FEATURE: arrdelay_mean_7d_car_od / arrdelay_mean_14d_car_od [ARR]
  What it is: Average arrival delay for this carrier on this OD pair (all
              flight numbers) over past 7 or 14 days. Captures route-level
              trends beyond a single flight number.
  FlightLabs: From offline Tier-2 cache: filter airline_iata + dep_iata +
              arr_iata + date window. Compute mean of arr_delayed.

FEATURE: arrdelay_count_7d_car_od / arrdelay_count_14d_car_od [ARR]
  What it is: Count of carrier OD flights over past 7 or 14 days.
  FlightLabs: Count of matching Tier-2 cache records.

FEATURE: arrdelay_median_7d_car_od [ARR]
  What it is: Median arrival delay for carrier on this OD pair over past
              7 days.
  FlightLabs: Tier-2 cache records. Compute median of arr_delayed.


────────────────────────────────────────────────────────────────────────────────
3I. AIR TIME HISTORY FEATURES [ARR only]
────────────────────────────────────────────────────────────────────────────────

"Air time" captures whether this route has been taking longer than scheduled
en-route recently (headwinds, unusual routing, holding). It is computed as
actual block time (gate-to-gate) from FlightLabs data, which includes taxi
time but is still a strong proxy for en-route duration.

actual_block_min = (arr_actual − dep_actual) in minutes
  From Endpoint A: (arrival.revisedTime − departure.runwayTime)
  From Endpoint B: (arr_actual − dep_actual) timestamps

FEATURE: airtime_mean_7d_fn_od / airtime_mean_14d_fn_od [ARR]
  What it is: Average actual gate-to-gate time for this flight number + OD
              pair over past 7 or 14 days. If actual block time is growing
              relative to schedule, arrival delays will follow.
  FlightLabs: Endpoint A records (same call as Section 3F/3H). Compute
              mean of actual_block_min for records in each date window.

FEATURE: airtime_n_7d_fn_od / airtime_n_14d_fn_od [ARR]
  What it is: Count of valid observations for the airtime mean.
  FlightLabs: Count of Endpoint A records with both runwayTime and
              revisedTime available (i.e. flight operated, not cancelled).

FEATURE: airtime_mean_7d_car_od / airtime_mean_14d_car_od [ARR]
  What it is: Average block time for this carrier on this OD pair (all
              flight numbers) over past 7 or 14 days.
  FlightLabs: Tier-2 cache: filter airline + dep + arr + window.
              Compute mean of (arr_actual − dep_actual) in minutes.

FEATURE: airtime_n_7d_car_od / airtime_n_14d_car_od [ARR]
  What it is: Count of valid observations for carrier OD airtime mean.
  FlightLabs: Count of Tier-2 cache records with non-null actual times.


────────────────────────────────────────────────────────────────────────────────
3J. WHEELS-OFF SLIP FEATURES [ARR only]
────────────────────────────────────────────────────────────────────────────────

"Wheels-off slip" in BTS is actual departure minus scheduled departure —
essentially departure delay. The "origin_blk" variant groups all flights
at origin by departure time block rather than by flight number, to capture
structural time-of-day congestion patterns that affect a whole time slot.

FEATURE: wo_slip_mean_7d_fn_od / wo_slip_mean_14d_fn_od [ARR]
  What it is: Average departure delay for this flight number + OD pair over
              past 7 or 14 days (same value as flightnum_od_depdelay_mean
              for those windows). Used in the arrival model as a named
              predictor of how much pre-departure slip this flight typically
              accumulates, which directly eats into the en-route time buffer.
  FlightLabs: Endpoint A records. Compute mean of dep_delay_min.
              (Same records already fetched for Section 3F.)

FEATURE: wo_slip_n_7d_fn_od / wo_slip_n_14d_fn_od [ARR]
  What it is: Count of observations for the slip mean.
  FlightLabs: Count of Endpoint A records in the window.

FEATURE: wo_slip_mean_7d_origin_blk / wo_slip_mean_14d_origin_blk [ARR]
  What it is: Average departure delay at this origin airport in this
              departure time block (e.g. all 14:00–14:59 departures) over
              past 7 or 14 days. Captures structural, time-of-day congestion
              at the origin that applies regardless of flight number.
  FlightLabs: Tier-2 offline cache for dep_iata = Origin (all carriers).
              Derive DepTimeBlk from dep_time. Filter on matching block.
              Compute mean of dep_delayed over each window.

FEATURE: wo_slip_n_7d_origin_blk / wo_slip_n_14d_origin_blk [ARR]
  What it is: Count of valid departures in this origin + DepTimeBlk + window.
  FlightLabs: Count of matching Tier-2 cache records.


────────────────────────────────────────────────────────────────────────────────
3K. DESTINATION ROLLING DELAY STATISTICS [BOTH]
────────────────────────────────────────────────────────────────────────────────

FEATURE: dest_depdelay_mean_last1 / last7 / last14 [BOTH]
  What it is: Average departure delay at the destination airport (all airlines)
              over the past N days. Used as a proxy for how operationally
              strained the destination is. A busy, delayed destination means
              aircraft must hold or sequence, adding arrival delay.
  FlightLabs: Tier-2 offline cache: all records with dep_iata = Dest (any
              airline). Compute mean of dep_delayed over each window.
              (Data is already collected if Dest is in the nightly airport
              list; for spoke airports that are only destinations, a separate
              nightly pull may be needed.)

NOTE: dest_lateaircraft_rate is DROPPED (delay cause code — see Section 3F).


────────────────────────────────────────────────────────────────────────────────
3L. DESTINATION ARRIVAL CONGESTION [ARR only]
────────────────────────────────────────────────────────────────────────────────

FEATURE: dest_arrivals_pm60_sched [ARR]
  What it is: Count of all scheduled arrivals at the destination airport
              within ±60 minutes of this flight's scheduled arrival time.
              A congested arrival window forces sequencing holds.
  FlightLabs: Tier-3 Call 2 (Future Flights at Dest, type=arrival).
              Count all records where |sortTime − target_arr_time| ≤ 60 min.
              No extra API call needed.

FEATURE: dest_airline_arrivals_pm60_sched [ARR]
  What it is: Same ±60-minute arrival count but only for the same airline.
              Captures gate congestion specific to the operating carrier.
  FlightLabs: Same Future Flights response (Call 2); filter carrier.fs ==
              target_airline_iata before counting.

FEATURE: dest_arrivals_pm60_eta [ARR]
  What it is: Count of arrivals at destination within ±60 minutes of the
              estimated (ETA) arrival time. For a pre-departure prediction,
              the ETA is unknown, so this is treated as identical to the
              scheduled version above.
  FlightLabs: Approximated as dest_arrivals_pm60_sched. In a system updated
              in-flight (e.g. for en-route predictions), use the current
              estimated arrival from real-time data to recompute the window.

FEATURE: dest_airline_arrivals_pm60_eta [ARR]
  What it is: Same as dest_arrivals_pm60_eta, airline-filtered.
  FlightLabs: Same approximation; use airline-filtered count from Call 2.

SECTION 4 — FEATURES DROPPED FROM LIVE PIPELINE
================================================================================

The following features trained against BTS data cannot be reliably produced
from FlightLabs or any other public pre-departure data source:

  CATEGORY 1 — Delay cause codes (not available in real time):
    carrier_lateaircraft_rate_last1/7/14
    origin_lateaircraft_rate_last1/7/14
    origin_nas_rate_last1/7/14
    origin_weather_rate_last1/7/14
    dest_lateaircraft_rate_last1/7/14
    tail_lateaircraft_rate_last1/7/14
    hub_{0,1,2,3,4}_lateaircraft_rate_last{1,7,14}
      (WN v7g mapping: hub_0=DEN, hub_1=PHX, hub_2=BWI, hub_3=MDW, hub_4=BNA)

  CATEGORY 2 — Tail-specific delay history (tail assignment not knowable
               pre-departure without internal records):
    tail_depdelay_mean_last1/7/14

RECOMMENDATION: Retrain the model variants with these features excluded and
with the remaining features sourced from FlightLabs. This ensures the model
learns appropriate weights for the reduced feature set rather than relying on
correlations with the dropped features. Expected AUC impact: −0.010 to −0.020
based on typical feature importance of these columns in the BTS-trained model.

SECTION 5 — SUMMARY: CALL BUDGET PER PREDICTION
================================================================================

TIER 1 — One-time setup (amortized to near-zero):
  ~100 calls to Airports endpoint; static files for type mapping and FAA age.

TIER 2 — Nightly batch (shared; not charged per prediction):
  ~50 airports × 2 calls (dep + arr) = 100 calls per airline per night
  + 5 hub airports × 1 all-carrier call = 5 calls
  TOTAL: ~105 FlightLabs calls per airline per night

TIER 3 — Per-prediction at request time:
  Call 1: Future Flights at Origin            – always (1 call)
  Call 2: Future Flights at Destination       – always (1 call)
  Call 3: Flight Data by Date (flight number) – only if not cached (1 call,
                                                TTL ~12 h; covers 14-day window)
  Weather:                                    – Open-Meteo, 2 calls, free
  TOTAL FlightLabs per prediction: 2 (cached) to 3 (first prediction of day)
