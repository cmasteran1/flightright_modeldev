**Date:** 2026-04-16
**Target:** Binary ordinal heads at thresholds `[15, 30, 60, 120]` for dep/arr; binary cancellation classifier for the cross-airline cancel model.
**Primary Metric:** Per-threshold AUC on unbalanced eval, maximized jointly across all four thresholds via **shared-params** mean AUC (see "Metric Choice" below).
**Baseline:** v10 optimum, carried into v11 configs unchanged: `depth=8, learning_rate=0.03, l2_leaf_reg=3.0, iterations=6000, od_wait=200, seed=1337`. v11 smoke AUC at ge120 landed at 0.803 with these settings (but on a 1-month, 50%-balanced sanity slice — not a valid baseline; full-scale numbers to come).
**Best trial:** Not yet run. This document is the sweep design.

## 1. Search Space

Existing search space in `src/training/hyperparam_optimize.py::suggest_catboost_params` is already well-designed. **Recommendation: keep it unchanged.** The v10 optimum sits comfortably within every range, and v11's feature shifts are modest enough that widening is not needed.

| Parameter | Type | Range | v10 optimum | Rationale |
|-----------|------|-------|-------------|-----------|
| `depth` | int | [4, 12] | 8 | 8 is mid-range; exploration in both directions is valuable given the v11 feature-set change. |
| `learning_rate` | log-float | [0.005, 0.15] | 0.03 | Log-scale covers ~30x range. 0.03 sits below midpoint in log space. |
| `l2_leaf_reg` | log-float | [0.5, 20.0] | 3.0 | Might prefer higher reg in v11 — OTP rate has 7% missingness and cancel anomaly has tail-distributed values. Log-scale handles this. |
| `iterations` | int step 500 | [2000, 10000] | 6000 | Early stopping via `od_wait` means actual iterations used is usually well below ceiling. |
| `od_wait` | int step 50 | [50, 500] | 200 | 200 is safely inside; smaller values risk premature stops on noisy ge120 labels. |
| `random_strength` | float | [0.0, 5.0] | — (default 1.0) | Not in v10 config; worth exploring for class imbalance at ge120. |
| `border_count` | int | [32, 255] | — (default 254) | Low-impact for CatBoost; keep for completeness but expect flat response. |
| `min_data_in_leaf` | int | [1, 100] | — (default 1) | Sparse ge120 (3.3% base) benefits from higher values to avoid overfit. |
| `bootstrap_type` | categorical | Bayesian / Bernoulli / MVS | — | MVS often wins for binary imbalanced with long right tails (our exact setup). |
| `bagging_temperature` | float | [0.0, 5.0] | — | Only under Bayesian bootstrap. |
| `subsample` | float | [0.5, 1.0] | — | Only under Bernoulli/MVS. Prior WN sweeps found ~0.8 optimal. |

**No changes to the search space function.** The v10 defaults appear in the ranges' interior and TPE will explore around them naturally.

### Why not widen further

The biggest v11 shift is threshold bucket change, not feature change. The new buckets are structurally different from v10's `[15,30,45,60]`, but:
- Each bucket is still a binary "DepDelay >= T" classification.
- CatBoost's best-response surface for such a classifier depends on feature signal and class imbalance, not on the absolute delay threshold.
- New features (OTP rate, cancel anomaly) move feature importance around but do not fundamentally change the hypersurface geometry.

Optuna's TPE will pick up on any shift naturally within 50 trials.

## 2. Metric Choice

### Primary: **shared-params mean AUC across `[15, 30, 60, 120]`**

Rationale:
1. **Each threshold is trained as a separate CatBoost model** (4 binary classifiers per airline per dep/arr), but in v11 production blueprints all four heads share the same hyperparameter config. Optimizing the hyperparameters *jointly* for average AUC therefore matches the deployment reality.
2. **Shared-params avoids 4 different optima per airline** that can't be merged into one deployable config.
3. **AUC is defined even for sparse classes** (unlike precision/recall which need a threshold cutoff). The existing script already enforces this at line 437: `if len(np.unique(bundle["y_eval"])) < 2: return 0.5`.

### Secondary (log only, don't optimize)

- **Per-threshold AUC** — logged by `make_shared_objective` as `auc_ge15`, `auc_ge30`, `auc_ge60`, `auc_ge120`. Lets you spot trials that win on mean AUC but lose badly on `ge120`.
- **Multibin log-loss** — captures bin-distribution calibration. Not in the current HPO objective (script only reports per-threshold AUC); can be eyeballed in MLflow UI after the fact from the final evaluation.

### Do NOT use per-threshold optimization as the main loop

`make_per_threshold_objective` exists and could find per-threshold-best configs. Skip it:
- Produces 4 configs per airline that can't be deployed together.
- Burns trial budget 4x with no gain over shared mode for the joint deployment.
- The per-threshold CLI path (--thresholds 15,30 etc.) is useful for debugging specific thresholds in isolation; reserve for post-hoc investigation.

### Sparse ge120 bucket: a known risk

At 3.3% base rate on the smoke slice, the ge120 bucket has:
- ~50x fewer positives than ge15 at full scale (1.6M rows → ~53k positives for ge120, vs ~530k for ge15).
- AUC variance ~3-5x higher than for ge15 on the same eval size.

**Mitigation:**
1. Use the **unbalanced eval set** (~240k rows after 15% random eval split on WN full), not the balanced training set, for the AUC computation. The existing `_train_and_evaluate` does this correctly.
2. If ge120 AUC swings by ±0.02 across trials with similar mean AUC, that's noise, not signal. Don't over-interpret.
3. If the sweep seems to prefer configs that sacrifice `auc_ge120` for tiny gains at `auc_ge15`, consider rerunning with a weighted mean (e.g., 0.25/0.25/0.25/0.25 → 0.15/0.20/0.30/0.35 to shift weight toward sparse buckets). **But first** run the default 50 trials and see if this is even a problem.

## 3. Trial Budget

### Per-airline, per-model-type: 50 trials

**Why 50, not 100:**
- Each trial trains 4 CatBoost models end-to-end with up to 10,000 iterations each, then isotonic-calibrates them, then evaluates on unbalanced eval.
- Rough budget: on full WN data (~1.6M rows, ~78 features), a single trial takes **10-30 min** on a 32-core machine with 64 GB RAM (revised upward from the original 8-15 min estimate after local pilot — see `2026-04-17-v11-hpo-local-pilot.md` F4; depth-11 MVS trials are the slow tail). 4 airlines × 50 trials × ~18 min avg = ~60 hours of wall-clock.
- TPE needs at least its `n_startup_trials=20` warmup before it starts exploiting. **Do not run fewer than 30 trials per threshold** — fewer means TPE never exits random search. 50 stays the recommendation (20 startup + 30 TPE-guided).
- 100 trials buys ~0.2% extra AUC at ~2x the wall-clock; not worth it for v11.

### Overall v11 budget

| Family | Airlines | Trials each | Total trials | Wall-clock |
|--------|----------|-------------|--------------|------------|
| Departure | WN, AA, DL, UA | 50 | 200 | ~40h (serial) / ~10h (4-parallel) |
| Arrival | WN, AA, DL, UA | 50 | 200 | ~40h (serial) / ~10h (4-parallel) |
| Cancel (cross-airline) | 1 model | — (manual) | — | — |
| **Total** | — | — | **400 trials** | **~40-120h depending on parallelism** (revised after local pilot) |

### Budget-constrained alternative

If compute is tight, do **WN only, dep+arr**. WN is the most-studied airline in this repo and its sweep results transfer decently to AA/DL/UA (per v10 history). That reduces the sweep to **100 trials, ~16h serial**. Accept that AA/DL/UA will inherit WN's tuned config.

### Subsampling for faster trials (optional)

`hyperparam_optimize.py` supports `--max-train-rows` and `--max-eval-rows`. Using them is a double-edged sword:
- Pro: cuts wall-clock 2-5x.
- Con: sparse ge120 bucket becomes even noisier on subsampled data.

**Recommendation:** only use `--max-train-rows 500000` on the departure sweeps (keeping ~30% of the 1.6M WN rows). Do NOT subsample the eval set (`--max-eval-rows 0`) — we need the full unbalanced eval for stable AUC at ge120.

## 5. Caveats and Watchlist

### Caveat 1: `airline_cancel_rate_anomaly_7d` signal on HPO

The correlations report (Task c) showed near-zero signal on the 1-month smoke slice because June 2025 had no major disruption events. Full-year 2023-2025 data has multiple disruption windows (Dec 2022 meltdowns, Jul 2024 CrowdStrike outage, etc.).

**Expected behavior in HPO:** if the full-year data reveals the feature has real signal (~0.08 Spearman vs ge60 from prior research), trials that include it will slightly outperform a version without it. If signal is still weak, the feature won't be a deciding factor — that's fine, it stays in the model but doesn't drive HPO.

**Watchlist:** after the sweep, pull per-feature importance from the best trial's CatBoost model (not captured by HPO MLflow — requires a follow-up `feature_importance_loss.csv` inspection). If `airline_cancel_rate_anomaly_7d` ranks below the 60th percentile of features, consider disabling it in v12.

### Caveat 2: sparse ge120 AUC variance

Already discussed in §2. If trial-to-trial `auc_ge120` swings wildly (>0.03) on similar mean AUCs, the top-5 ranking by mean AUC may be unstable. Tiebreak by:
1. Multibin log-loss (lower is better) computed post-sweep.
2. `auc_ge60` as a proxy for severe-delay quality (also sparse but less so at 10.4% base rate).

### Caveat 3: feature set change vs v10 sweep results

If the user has an old v10 HPO report with winning configs, those numbers **are not directly comparable** to v11 results. The feature set shifted. Use v10 optima as a seed baseline for the first trial of each v11 HPO run (Optuna will do this naturally via warm-start if we log them as "enqueue_trial"; with TPE they converge to the basin within ~5-10 trials anyway).

### Caveat 4: No HPO for cancellation model

`hyperparam_optimize.py` only supports `dep` and `arr`. For the cancel model, options:

A. **Keep v10 optima unchanged in v11** (current state). Low risk — the v10 cancel model didn't use the dropped NAS feature as a driver (cancel model feature importance was weather-led); stripping it should have minimal effect on optimal hyperparameters.

B. **Manual gridsearch post-sweep.** Once dep/arr sweeps complete, spot-train 3-5 variants on the cancel config and pick the winner. Budget: ~2h per variant, so ~10h manual.

C. **Extend `hyperparam_optimize.py`** to support cancel mode. Out of scope for this HPO plan; flag for v12.

**Recommendation: A for v11.** Revisit in v12 if cancel model metrics regress.

### Caveat 5: v11 smoke vs full-scale HPO

The smoke AUC of 0.803 at ge120 is NOT a useful baseline — it's computed on a 1-month balanced 50/50 slice of 480 rows. The first full-scale v11 training run (before HPO) is the real baseline. The sweep's job is to improve on THAT number.

## 6. Success Criteria

An HPO run is a success if:

1. **Best trial mean AUC ≥ v11 baseline (first full-scale training with v10 hyperparameters) + 0.002.** A 0.002 gain across 4 thresholds is the smallest gain that typically survives a holdout change. Anything less is noise.
2. **No trial's individual `auc_ge120` is more than 0.02 below the v11 baseline.** Avoids configs that win on easy thresholds but sacrifice sparse-class performance.
3. **Iteration count at convergence is well below the max (10,000).** If best trials all hit the ceiling, the search space is too tight; widen iterations and rerun.
4. **MLflow logs cleanly with parent + nested child runs.** Verifies the HPO plumbing, which is valuable for the next version.

   ```
   Config A: depth=8,  lr=0.03, l2=3.0  (v10)
   Config B: depth=6,  lr=0.05, l2=5.0  (shallower, more regularized)
   Config C: depth=10, lr=0.02, l2=10.0 (deeper, very regularized)
   Config D: depth=8,  lr=0.05, l2=1.0  (v10 depth, more aggressive lr, less reg)
   Config E: depth=8,  lr=0.03, l2=3.0, random_strength=2.0  (extra class-imbalance regularization)
   ```
2. Create `data/cancel_train_v11_hpoA.json` etc. by copying `data/cancel_train_v11.json` and editing the hyperparameters.
3. Run each:
   ```
   .venv/bin/python src/training/train_cancellation_catboost.py data/cancel_train_v11_hpoA.json
   ```
4. Compare via MLflow experiment "cancellation" → `roc_auc`, `average_precision`, `brier`, `log_loss`.
5. Pick winner, promote to `cancel_train_v11.json`.

Budget: ~10h manual (5 configs × ~2h each).
